# Цель: Loop Habit Tracker → Flutter (iOS · Android · macOS)

## Что делаем

Переносим приложение с Kotlin/Android на Flutter один в один: тот же функционал, тот же
дизайн, но запускается на iPhone, Android и Mac. Kotlin-код остаётся эталоном до конца и
удаляется одним коммитом только после достижения полного паритета.

## Источник истины

`docs/parity/FEATURES.md` — реестр из **352 фич** и **3000 правил поведения**, снятых с
Kotlin-кода. У каждого правила стабильный id вида `models.entry-values#4`. Реестр — это
определение готовности: каждая неотмеченная галочка есть работа.
Дизайн: `docs/superpowers/specs/2026-08-23-flutter-migration-design.md`.
План: `docs/superpowers/plans/flutter-migration-plan.md`.
Прогресс: `docs/parity/PROGRESS.md` — обновляется после каждого слайса.
Отклонения от оригинала: `docs/parity/DEVIATIONS.md`.

## Цикл

Единица работы — слайс: одна фича реестра со всеми её правилами.

1. **Взять** неотмеченную фичу из реестра.
2. **RED** — каждое правило превратить в Dart-тест, цитирующий id правила. Тесты падают.
3. **GREEN** — портировать код из Kotlin, минимально до зелёного.
4. **Прогон** — `dart test` + `flutter test` (вкл. golden) + запуск на iOS и Android.
5. **Аудит слайса** — сверить Kotlin-исходники фичи с написанными тестами. Всё
   неотражённое становится новыми пунктами реестра.
6. **Галочка** — ставится только если тесты зелёные И фича работает на обеих платформах.

**Выход из цикла:** ноль неотмеченных пунктов И финальный сквозной аудит не порождает
новых. Пока аудит порождает пункты — цикл продолжается.

## Инвариант

`uhabits-flutter/packages/uhabits_core` не импортирует `package:flutter`. Проверяется
тестом в CI. Ядро общается с платформой только через свои интерфейсы: `Database`, `Files`,
`Storage`, `Canvas`, `NotificationTray`, `TaskRunner`.

## Правило неисправления

Реестр содержит правила, описывающие баги оригинала (например `models.entry-values#6`:
числовое значение 3 неотличимо от SKIP). Порт воспроизводит их. Исправление допустимо, но
требует записи в `DEVIATIONS.md` с id правила и причиной.

## Волны

W0 скелет до запуска на трёх платформах · W1 модели и скоринг · W2 персистентность
(схема сразу с `uuid`/`updated_at`/`deleted_at`) · W3 команды и undo · W4 Canvas и графики ·
W5 экран списка · W6 экран привычки · W7 редактор и диалоги · W8 настройки и темы ·
W9 уведомления · W10 импорт и экспорт · W11 локализации · W12 виджеты (нативно: Glance +
WidgetKit) · W13 macOS · финальный аудит.

Каждая волна заканчивается запускаемым приложением и зелёным прогоном.

## Правила автономной работы

- **Не останавливаться и не спрашивать.** На вопрос «делать или не делать» — делать.
  Развилку решать самому, решение записывать в `DEVIATIONS.md` или в план.
- **Коммитить часто**, малыми осмысленными коммитами, в ветку `flutter-migration`.
  В сообщении коммита цитировать id фич реестра.
- **Не терять состояние.** После каждого слайса: обновить галочку в реестре, дописать
  строку в `PROGRESS.md`, закоммитить. Работа должна переживать обрыв сессии.
- **Не смягчать гейты.** Тест не удаляется и не ослабляется, чтобы позеленело. Если
  правило реестра не удаётся выполнить — записать в `DEVIATIONS.md` и идти дальше.
- **Не чинить, не улучшать, не рефакторить оригинал.** Только порт.
- **Тупик — не повод остановиться.** Заблокированный слайс отмечается `BLOCKED` в
  `PROGRESS.md` с причиной, работа продолжается на следующем.
- **Отчёт утром** — что сделано, что зелёное, что заблокировано, где мы в реестре.

## Фазы после паритета

Фаза 2 — синхронизация между устройствами (схема к ней уже готова, скрытые строки настроек
Sync server / Sync key / Encryption key портируются как есть). Фаза 3 — переработка дизайна
под платформы. Обе начинаются только после нуля неотмеченных пунктов.
